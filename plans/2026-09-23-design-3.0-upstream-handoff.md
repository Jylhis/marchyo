Date: 2026-09-23. Context: marchyo (github:Jylhis/marchyo) adapted to
jylhis-design 3.0.0 in commit 8412248 ("feat(theme)!: adopt jylhis-design
3.0.0"). marchyo's flake.lock pins github:Jylhis/design @ e24a796d

## Consumer contract marchyo now relies on (please keep stable)

1. themes/jylhis.json is the single theme (light "Print" / dark
   "Negative"). Palette/status/syntax/ansi keys with per-mode values are
   read at eval time directly from the flake input (no build). Any token
   rename or hex retune propagates into every marchyo surface — that is
   intended, but a schema change (dropping a section, renaming a mode key)
   breaks marchyo eval immediately.
2. Theme/asset names: jylhis-dark / jylhis-light (was jylhis-field /
   jylhis-sheet; ghostty files, bat tmThemes, base16 YAMLs, kvantum).
   Internal tmTheme/base16 names are "Jylhis Dark" / "Jylhis Light".
3. Committed snapshots must stay committed and byte-identical to
   generator output:
   - platforms/gtk/jylhis-{light,dark}.css (NEW, see below)
   - platforms/waybar/style.css (+ _reference pair)
   - platforms/mako/config (+ _reference pair)
   - platforms/shadcn/tokens.css
   marchyo reads these as eval-time TEXT. If any is dropped from git,
   marchyo's flake check fails. The generator refreshes them in-tree;
   please keep the determinism gate covering them.
4. Generated-only assets (ghostty themes, bat tmThemes, base16 yamls,
   console nix, fzf sh, rofi, gimp, emacs themes, hyprland confs) are
   consumed via the built pkgs.jylhis-themes package as PATH references
   (nix/themes.nix). marchyo's overlay callPackages
   <input>/nix/themes.nix directly on all platforms (the flake overlay
   output is Linux-only from marchyo's perspective; darwin hosts also
   install ghostty themes this way).
5. The upstream HM module (nix/home-manager-module.nix) is imported with
   EVERY target disabled. Reason: its gtk/mako/waybar targets
   builtins.readFile the built themes package at eval time, which is
   import-from-derivation — forbidden on marchyo's build infra
   (nixbuild.net). Not a bug upstream, just a hard consumer constraint.
   Consequence: if you change option names in that module (mode/name/
   *.enable), marchyo's jylhis-theme.nix must be updated in lockstep —
   a rename silently breaks marchyo eval (undefined option error).

## Commits landed in j10s projects/design during this work

- f4d7b193d fix(design): anchor generated root outputs in .gitignore
  ROOT CAUSE FIX. The bare `tokens.css` gitignore pattern matched at any
  depth, so the tracked, hand-maintained platforms/shadcn/tokens.css
  (and platforms/_reference/shadcn/tokens.css) were IGNORED. In j10s
  itself git keeps tracking them (already tracked), but every publish
  snapshot (fresh git init + git add -A in just/publish.just) silently
  dropped both files. Result: the first 3.0.0 publish (7570df3) shipped
  a jylhis-themes package that failed to build:
    install: cannot stat '.../platforms/shadcn/tokens.css'
  marchyo's nix flake check died on it. Fix: anchor root outputs
  (/tokens.css, /tokens-data.js, /density.css, /_ds_bundle.js).
  FOLLOW-UP FOR YOU: the publish pipeline has no completeness gate —
  nothing verifies the snapshot against the install-map. Consider a
  publish check that builds nix/themes.nix from the exported tree (or at
  least `install -D --dry-run`s every install-map src) before push.

- 5e1321535 feat(design): commit the per-polarity gtk css snapshots
  platforms/gtk/jylhis-{light,dark}.css are now committed (removed from
  nix/generated-files.nix registry and .gitignore), so nix/themes.nix
  routes them from src like the waybar/mako legacy copies. Rationale:
  IFD-free consumers need per-polarity GTK text at eval time; the
  in-derivation generation alone cannot provide it. The generator still
  writes both files on every run (verified byte-identical; determinism
  gate passes). The share/jylhis/gtk/ package output is unchanged.
  NOTE: this partially reverses the spirit of 4966e7eb7 ("sources only
  in git") — if you want a different mechanism (e.g. an eval-safe
  lib export), coordinate with marchyo before removing the snapshots.

- a15ed13af fix(design): purge v2 drift hexes from the waybar targets
  The _reference waybar files carried pre-3.0 hexes that no v3 token
  maps, surviving the identity recolor into every generated copy:
    dark ref:  #221c14 (accent-subtle), #8b8f96 (text-faint)
    light ref: #f0e8dd (accent-subtle), #8a5000 (status-warn),
               #005a5f (syn-type)
  marchyo's runtime theme switch translates surfaces by semantic-token
  hex replacement; unmapped hexes break variant switching (a dark hex
  stays dark after switching to light). All hexes in both waybar
  polarity references are now exact v3 token values. Verified with the
  palette audit (zero non-token hexes in both files).

## Known upstream state you may want to fix (not blocking marchyo)

- Other _reference files still carry non-token hexes: ghostty refs
  (ansi brights like #70b900/#ff7f7f, selection-background #2b3446 /
  #dfe6f2), mako critical backgrounds (#3a1f1c dark / #f5e0dc light,
  ad-hoc). marchyo does not runtime-swap those surfaces (its mako config
  derives from the palette module directly; ghostty themes are applied
  by-name, not hex-swapped), so they are cosmetic upstream drift only —
  but if any future consumer hex-translates them, they will bite the
  same way waybar/fzf did.
- The legacy light gtk.css (platforms/gtk/gtk.css, generated-only) still
  exists for name-hardcoding consumers; marchyo no longer uses it.
- packages/marchyo-shell embeds a QML fallback palette that now includes
  the new `destructive` token — if 3.x adds further palette tokens,
  expect marchyo's shell Theme.qml fallback to want them too.
